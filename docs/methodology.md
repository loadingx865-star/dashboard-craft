# 看板前端开发全流程方法论

> 版本 1.0 · 2026-09-18
> 配套可安装 Skill：`skills/dashboard-craft/`

---

## 一、为什么需要这份方法论

### 1.1 问题不是"AI 不够强"，而是"没有规范层"

用 AI 辅助开发看板时反复出现的问题，本质是三类：

| 问题 | 真实表现 | 根因 |
|---|---|---|
| **适配漂移** | 开发时用 1920×1080 笔记本，现场是 4K 电视/拼接屏，字号过小、布局溢出、图表模糊 | 开工前没锁定交付环境 |
| **风格断层** | 第二期看板配色、字号、图表样式与第一期不一致 | 设计决策没有单一真源，每次现场发挥 |
| **拼凑实现** | 功能能跑，但组件各写各的，越开发越乱 | 没有组件与图表的统一入口 |

这三类问题的共同点：**都不是编码能力问题，而是流程与约束问题**。

### 1.2 为什么"多装几个 skill"解决不了

市面上流行的前端 skill（frontend-design、shadcn、vercel-react-best-practices、playwright 等）都是**单点能力增强**——它们提升某一环节的质量，但**不提供编排、约束与门禁**。

它们之间的关系是：

```
单点 skill  = 更强的工具
本方法论     = 决定"什么时候用哪个工具、产出必须满足什么标准、不达标怎么办"
```

没有后者，前者只会让你更快地生产出不规范的东西。

### 1.3 关于 skill 的一个重要认知

**不是装得越多越好。** 每个 skill 都会占用上下文并可能产生规则冲突（例如表达能力型页面的 frontend-design 与看板所需的克制风格会打架）。正确做法是：

- 按**项目类型**精选 skill（看板类：组件、图表、性能、测试为主）；
- 用**本方法论作为编排层**，明确每个 skill 在哪个阶段生效；
- 定期清理不再使用或已被吸收的 skill。

## 二、核心思想：三道防线

### 防线一：约束前移

把适配问题从"交付前"提前到"开工第一天"。

- 环境约束卡（终端/浏览器/缩放/观看距离/数据频率/网络）必须先填完。
- 骨架先行：先搭布局壳并在全部目标分辨率验证通过，再填内容。
- 收益：改动成本从"内容量成正比"降到"几乎为零"。

### 防线二：单一真源

让设计决策只在一个地方定义。

- `design-tokens.json`（机读）+ `MASTER.md`（人读）+ `pages/*.md`（受限偏离）。
- 冲突裁决顺序：token > MASTER > 页面覆盖 > 现有代码。
- 收益：换主题只改一处；第二期开发自然继承第一期风格。

### 防线三：验证门禁

用可复现的自动化检查替代"肉眼看着差不多"。

- 分辨率 × 浏览器矩阵截图 + 视觉回归。
- 性能预算、可访问性、冒烟测试。
- 收益：交付有证据、退化可发现、问题可追溯。

## 三、八阶段流程

```
阶段 0  约束锁定      →  阶段 1  设计单一真源   →  阶段 2  规格与拆票
                                                          ↓
阶段 7  交付存档      ←  阶段 6  质量门禁       ←  阶段 5  适配验证
        ↑                                                 ↑
        └──────────  阶段 4  组件与图表  ←  阶段 3  骨架先行
```

| 阶段 | 名称 | 核心产出 | 通过条件（Gate） |
|---|---|---|---|
| 0 | 约束锁定 | 环境约束卡 | 分辨率/浏览器/缩放/网络/数据频率全部明确 |
| 1 | 设计单一真源 | design-tokens + MASTER | token 通过校验；图表与缩放策略成文 |
| 2 | 规格与拆票 | spec + 纵向切片任务 | 每票有可验证验收标准与依赖 |
| 3 | 骨架先行 | Layout Shell | 空骨架在全部目标分辨率不破版 |
| 4 | 组件与图表 | 受限组件层 + 图表封装 | 无页面级临时样式；图表走封装 |
| 5 | 适配验证 | 多分辨率截图基线 | 矩阵跑通，无溢出/裁切/重叠 |
| 6 | 质量门禁 | 性能/a11y/测试报告 | 预算达标、冒烟全绿、diff 无意外 |
| 7 | 交付存档 | 交付包 + 基线资产 | 基线入库、回归资产可复跑 |

**五条铁律**（违背任一条即回退）：

1. 无约束不开发
2. 无真源不写样式
3. 无矩阵不交付
4. 一个概念一处实现
5. 偏离必须登记

## 四、关键决策点

### 4.1 大屏字号缩放策略（决定 90% 的返工量）

| 策略 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **等比缩放** | 固定设计稿尺寸，整体 scale | 与设计稿 100% 一致、实现简单 | 非 16:9 留黑边/裁切、极端缩放模糊 | 单一固定终端 |
| **断点重排** | 按断点切换布局与字号 | 适配各种分辨率与比例 | 成本高，需为每断点定义布局 | 终端类型多样 |
| **混合**（推荐多终端） | 外层缩放 + 内部极端时重排 | 兼顾一致性与适应 | 最复杂，需明确边界 | 多终端精细交付 |

**必须选定并写入真源**，禁止到开发中期再决定。

### 4.2 图表库唯一选型

看板推荐 **Apache ECharts**：canvas 渲染、大数据量性能好、主题系统完善、支持导出。

**一个项目只用一个图表库**，且必须封装唯一入口。禁止页面临时引入第二套图表库——这是风格断层最常见的来源。

### 4.3 断点必须来自真实终端

不要照抄通用网站断点。看板需要大屏专用档：

| 档位 | 典型宽度 |
|---|---|
| 超大屏/拼接 | ≥ 2560px |
| 4K 大屏 | 1920-2559px |
| 普通桌面 | 1280-1919px |
| 笔记本 | 1024-1279px |
| 兜底 | < 1024px（明确是否支持） |

## 五、AI 协作规则

### 5.1 任务下达模板（缺项不开发）

```markdown
## 任务
<一句话说明>

## 项目上下文
- 设计真源：design-system/MASTER.md
- Token：design-system/design-tokens.json
- 组件清单 / 图表封装位置：

## 环境约束
- 目标分辨率 / 浏览器 / 缩放 / 观看距离 / 数据频率

## 本次范围
- 要做：
- 不要做：

## 验收标准
- 可复现标准 1
- 可复现标准 2
```

### 5.2 禁止项（AI 产出前自检）

硬编码颜色/字号 · 引入新图表库 · 页面内直接实例化图表 · 跳过骨架 · 为单页造专用组件 · 擅自升级大版本 · 未确认改共享组件 · 用 `any` · 删测试 · 用 `!important` 掩盖问题

### 5.3 变更影响面分析

改动共享组件/图表封装/token/全局样式前，必须先输出：

```
本次改动：<文件/模块>
直接受影响：<依赖它的组件/页面>
需回归验证：<需重跑截图/测试的页面>
风险点：<可能的破版或行为变化>
```

### 6.2 一条重要边界

**frontend-design 与 design-taste-frontend 的主场是 landing / portfolio**。官方 frontend-design 明确说"dashboard for financial analysts"与玩具设计完全不同；社区版 taste-skill 更是直接声明**"不适用于看板、数据表格、多步产品 UI"**。

看板应借鉴它们的**反模板感与排版原则**，但不要照搬其"大胆表达"的取向——看板需要的是**克制、清晰、信息密度优先**。

```bash

npx skills list                           # 查看已装
```

**安装前务必用 `find` 复核当前热度**——本表是快照，生态变化很快。

## 八、如何支持后续持续更新

技术升级快，**任何写死版本的文档都会过期**。本方法论用三件事保证不过期：

### 8.1 记录角色，不记录版本

文档写"图表库首选 ECharts"，而不是"ECharts 5.4.2"。版本放在 `toolchain-baseline.json`，由脚本维护。

### 8.2 脚本实时拉取

```bash
python scripts/refresh_toolchain.py                  # 拉取最新并与基线对比
python scripts/refresh_toolchain.py --update-baseline # 确认后更新基线
```

脚本直接查 npm registry，永远反映真实最新版本。

### 8.3 季度复核

| 判断 | 动作 |
|---|---|
| 有新稳定版 | 评估是否升级 |
| 有更好替代品 | 记录，**不在冲刺期切换** |
| 有废弃/停维护 | 制定迁移计划 |
| 有安全公告 | 优先处理 |

**升级原则**：小步升级（逐个大版本升）· 升级必回归（跑完整门禁）· 禁止冲刺期跃迁 · 锁文件必须提交。

### 8.4 方法论自身也要演进

- 收集真实失败案例，**针对性修订**，而不是堆砌通用规则。
- 某阶段方法被证明无效时，**删掉它**。
- 版本号记录在 Skill 的 `metadata.version`，每次实质更新递增。

## 九、落地清单

### 新项目启动

- [ ] 填写环境约束卡（未完成不开工）
- [ ] 初始化 `design-system/`（token + MASTER）
- [ ] 选定大屏缩放策略
- [ ] 确认图表库唯一选型
- [ ] 建立组件清单
- [ ] 拆纵向切片任务
- [ ] 配置 Playwright 视口矩阵
- [ ] 接入 CI（token 校验 + 视觉回归 + 性能 + a11y）

### 每次交付前

- [ ] 矩阵内全部视口通过
- [ ] 视觉 diff 无未登记差异
- [ ] 无硬编码色值
- [ ] 性能预算达标
- [ ] a11y 无严重问题
- [ ] 冒烟全绿
- [ ] 基线入库、文档齐全、回滚已验证

### 项目结束后

- [ ] 资产沉淀为下个项目模板（约束卡/token/骨架/图表封装/测试配置）
