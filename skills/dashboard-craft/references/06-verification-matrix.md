## 目的

用可复现的自动化检查替代"肉眼看着差不多"。任何交付都必须有证据。

## 视觉回归

### 流程

1. 首次跑通后，将截图存为**基线**纳入版本管理。
2. 后续每次改动自动截图并与基线 diff。
3. 差异超过阈值 → 失败，人工确认是"预期改动"还是"回归"。
4. 预期改动 → 更新基线并记录原因。

### 检查项

- 像素差异比例
- 元素溢出 / 裁切（可用脚本检测 `scrollWidth > clientWidth`）
- 布局重叠
- 字体回退（实际渲染字体是否为目标字体）
- 意外滚动条
- 图表清晰度：用 scale 方案时，canvas 已按 `devicePixelRatio × scale` 补偿，放大后无锯齿、无发虚

### 工具选择

| 工具 | 说明 |
|---|---|
| Playwright 截图 + 内置 toHaveScreenshot | 推荐首选，生态好、CI 友好 |
| pixelmatch | 需要自定义像素比对时使用 |
| 平台化视觉测试服务 | 团队协作、需要集中管理基线时考虑 |

**注意**：视觉回归对字体渲染、抗锯齿、GPU 差异敏感。同一基线必须在**统一环境**（相同容器/相同浏览器版本）下生成与比对，否则会产生大量误报。跨机器比对时需容忍一定像素差异。

### 容差必须按视口分档

`maxDiffPixelRatio` 是**比例**，同一数值在大屏上会放大成极宽的绝对容差：

| 视口 | 像素总数 | `0.01` 对应的容差 |
|---|---|---|
| 1366×768 | 1.05M | ≈1.0 万像素（尚可） |
| 1920×1080 | 2.07M | ≈2.1 万像素 |
| 3840×2160 | 8.29M | **≈8.3 万像素（过松，会漏掉真实回归）** |

**规则**：4K 及以上视口不要用比例阈值，改用固定像素上限（如 `maxDiffPixels: 2000`），或把比例压到 `0.001` 量级。工厂大屏恰恰是最需要严格比对的场景。

### 设备像素比（DPR）必须进矩阵

阶段 0 记录了缩放与 DPI，验证矩阵就要覆盖它：至少补一档 `deviceScaleFactor: 2` 的视口。高 DPI 下才会暴露的问题：字体回退、canvas 图表模糊、1px 边线消失。只测 `deviceScaleFactor: 1` 等于没测电视与高分屏。

## 性能预算

设定明确数字，写进 CI：

| 指标 | 建议目标（看板类） |
|---|---|
| 首屏可交互 | 可按项目定，如 < 3s（内网环境放宽） |
| 主包体积 | 明确上限，超限失败 |
| 图表首帧 | 明确上限 |
| 长时间运行内存增长 | 8 小时增长 < 10%（示例阈值，按项目定） |

工具：Lighthouse CI、打包体积分析、`performance.memory`（仅 Chromium）或 Node 进程监控。

## 可访问性

- 文字对比度达标（大屏弱光环境下尤其重要）。
- 焦点可见（键盘操作场景）。
- 语义标签与 ARIA 正确。
- 不依赖颜色单独传达信息（色盲友好）。

工具：axe-core + Playwright。

## 冒烟测试

覆盖核心链路：打开页面 → 数据加载 → 关键交互 → 异常态。用 Playwright 脚本，每次构建自动执行。

## Gate 检查

机器判定：`python <skill>/scripts/check_gates.py --project . --stage 5` 与 `--stage 6`。
阶段 5 检查矩阵视口未被标记未测、且已登记基线位置；阶段 6 要求报告正文同时覆盖性能、可访问性、冒烟、视觉回归四类结论。

- [ ] 矩阵内全部视口截图通过
- [ ] 容差已按视口分档（4K 用固定像素上限或 ≤0.001 比例）
- [ ] 矩阵包含至少一档 deviceScaleFactor: 2
- [ ] 视觉 diff 无未登记差异
- [ ] 性能预算达标
- [ ] a11y 检查无严重问题
- [ ] 冒烟测试全绿
- [ ] 长时间运行内存曲线正常（如适用）
- [ ] 若选用 scale 方案：非设计稿比例、超宽拼接、缩放后字号下限已逐条验证，结论已记入报告
