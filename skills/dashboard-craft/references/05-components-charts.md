# 阶段 4 —— 组件与图表规范

## 目的

消灭"页面里各写各的样式"，让同类元素只有一个实现入口。这是解决"东拼西凑"的核心手段。

## 看板即组合：跨看板复用

**多期交付时，看板数量增加不应带来实现数量增加。** 每个看板本质上都是"同一套容器布局 + 图表/业务组件组合"，不同的只是配置：

```
看板 A ─┐
看板 B ─┼─→ 同一套图表与业务组件（唯一真源）
看板 C ─┘        ↑
           只有配置不同：数据源、槽位、标题、轮询周期
```

**要求**：

- 图表与业务组件跨看板**只有一个实现**。新增看板只允许新增**配置与布局编排**，不允许复制一份组件或图表代码再改。
- 看板之间的差异集中在**配置层**（页面配置 / 布局槽位 / 数据映射），不散落到组件内部。
- 修一个图表的样式或行为，所有引用它的看板同时生效。某个看板确实要例外时，走铁律 5 的页面级偏离登记，而不是复制代码。

**判定方式（人工确认项，不做机器判定）**：新增第 N 个看板时，检查代码 diff 是否为"新增配置 + 复用既有组件"。若 diff 里出现第二份图表/仪表盘实现，即违反铁律 4。这一条依赖代码评审，不写成 Gate，避免把口号包装成假门禁。

## 组件分层

```
基础组件层   Button / Input / Table / Tag / Icon   —— 来自 UI 库 + token 定制
业务组件层   StatusCard / MetricTile / AlarmList   —— 组合基础组件
图表层       Chart 封装（唯一入口）
页面层       仅负责布局与数据编排，不定义视觉样式
```

**页面层禁止做的事**：

- 禁止写硬编码颜色、字号、间距。
- 禁止内联复杂样式。
- 禁止为单个页面临时造一个"特殊卡片"。
- 若确有特殊需求 → 抽成业务组件，登记进组件清单。

## 组件清单（单一真源）

维护一份组件清单文档，记录：

| 字段 | 说明 |
|---|---|
| 组件名 | 唯一名称 |
| 用途 | 什么时候用 |
| 变体 | 支持的 props/变体 |
| 位置 | 文件路径 |
| 状态 | 稳定 / 实验 / 废弃 |

**新需求先查清单**：能用现有组件就不新造；确需新造则登记。禁止出现两个功能相同但名字不同的组件。

## 图表封装（重点）

图表是风格断层与性能问题的重灾区。要求**只有一个封装入口**。

封装必须统一处理：

| 职责 | 说明 |
|---|---|
| 自适应 | 用 `ResizeObserver` 监听容器，自动重绘 |
| 主题 | 从 design-tokens 读取色板与样式 |
| 空数据 | 统一空状态 |
| 加载态 | 统一 loading |
| 错误态 | 统一错误提示 |
| 销毁重建 | 组件卸载时正确 dispose，避免内存泄漏 |
| 大数据 | 超过阈值自动降采样或用 canvas 渲染 |
| 导出/截图 | 若需要，统一实现 |

**禁止**：

- 禁止在页面里直接 new 图表实例。
- 禁止引入第二个图表库（除非在阶段 1 明确登记）。
- 禁止每个图表单独定义配色。

## 性能注意点

- 大数据量图表优先 canvas（如 ECharts 默认）而非 SVG。
- 高频刷新图表要限流，或改用增量更新。
- 图表容器尺寸未确定时不初始化，避免 0 尺寸渲染错误。
- 长时间运行需验证无内存泄漏（反复切换页面观察内存）。
