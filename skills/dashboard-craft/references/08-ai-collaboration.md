# 贯穿线 —— AI 协作规则

## 目的

AI 是本流程的主要执行者。它的输出质量高度依赖**输入是否规范**与**禁止项是否明确**。这一节把"怎么和 AI 协作"变成可执行规则。

## 一、任务下达模板

每次让 AI 开发看板功能，用这个模板，缺项不开发。

```markdown
## 任务
<一句话说明要做什么>

## 项目上下文
- 项目路径：
- 设计真源位置：design-system/MASTER.md
- Token 位置：design-system/design-tokens.json
- 组件清单：
- 图表封装位置：

## 环境约束（来自阶段 0）
- 目标分辨率：
- 目标浏览器：
- 缩放：
- 观看距离：
- 数据刷新频率：

## 本次范围
- 要做：
- 不要做：（明确排除项）

## 验收标准
- 可复现的标准 1
- 可复现的标准 2

## 约束
- 只能使用现有组件与 token，禁止新增硬编码样式
- 改动共享组件前先列出受影响页面
```

## 二、禁止项清单

以下行为一律禁止，AI 产出前需自检：

| 禁止项 | 原因 |
|---|---|
| 硬编码颜色/字号/间距 | 破坏单一真源 |
| 引入新的图表库 | 破坏风格统一 |
| 因“设备老”就把源码一律写 ES5 | 用长期维护成本换一次性省事；应声明 Browserslist 目标后由构建链降级 |
| 新增看板时复制一份图表/仪表盘实现 | 违反铁律 4；应只新增配置与布局编排 |
| 在页面里直接实例化图表 | 绕过封装层 |
| 跳过骨架直接写页面 | 适配问题后移 |
| 为单个页面造"专用"组件 | 导致组件重复 |
| 擅自升级大版本依赖 | 引入不可控风险 |
| 未确认就修改共享组件 | 影响面不可控 |
| 用 `any` 绕过类型 | 埋下隐患 |
| 删除或跳过测试 | 丢失验证能力 |
| 在页面中使用 `!important` 掩盖问题 | 掩盖而非解决 |

## 三、变更影响面分析

改动以下任一类文件前，必须**先输出受影响清单**，确认后再改：

- 共享组件
- 图表封装层
- design-tokens
- 全局样式 / 布局壳
- 公共工具函数

输出格式：

```
本次改动：<文件/模块>
直接受影响：<依赖它的组件/页面>
需回归验证：<需要重跑截图/测试的页面>
风险点：<可能的破版或行为变化>
```

## 四、单一真源优先原则

出现冲突时的裁决顺序：

1. design-tokens（最高）
2. design-system/MASTER.md
3. pages/<page>.md（页面级覆盖）
4. 现有代码实现（最低）

**规则**：若代码与 token 不一致，以 token 为准，改代码。禁止"照着现有代码抄"来传播错误。

## 五、执行节奏

- 一次只做一张票，不要"顺便"扩大范围。
- 每完成一张票，立即在最小与最大分辨率自检。
- 视觉相关改动完成后，跑一次视觉回归。
- 遇到不确定的设计决策，**停下来问**，不要自己发挥。

## 六、自检清单（AI 提交前必查）

- [ ] 用的颜色/字号/间距全部来自 token
- [ ] 没有引入新的库或组件变体
- [ ] 新增看板为「配置 + 复用」，未复制图表/组件实现
- [ ] 未以“设备老”为理由把源码退回 ES5（如需降级，目标已写入 Browserslist）
- [ ] 图表走的是统一封装
- [ ] 改动共享资产时已列出影响面
- [ ] 在目标分辨率下自检过
- [ ] 测试通过，未删除测试
- [ ] 无 `any`、无 `!important` 掩盖问题

## 七、常见 AI 失误与对策

| 失误 | 对策 |
|---|---|
| 自作主张换配色 | 明确要求从 token 取值 |
| 写出"能跑但难看"的布局 | 骨架先行 + 视觉基线 |
| 反复重构同一样式 | 单一真源 + 禁止页面级样式 |
| 忽略分辨率 | 约束卡 + 矩阵门禁 |
| 引入多余依赖 | 依赖变更需审批 |
| 为“兼容老设备”把生产代码降到 ES5 | 改成声明 Browserslist + 开 @vitejs/plugin-legacy |
| 新增看板时重新实现一遍图表 | 看板即组合：只新增配置，复用既有组件 |
| 改 A 坏 B | 影响面分析 + 回归测试 |
