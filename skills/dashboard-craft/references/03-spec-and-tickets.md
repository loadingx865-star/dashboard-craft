# 阶段 2 —— 规格与拆票

## 目的

把设计真源翻译成 AI 能可靠执行、且可验证的任务。避免"一口气让 AI 写完整站"导致的失控与返工。

## 核心原则：纵向切片

**错误做法**（横向切片，容易烂尾）：
- 票 1：写完所有 API 层
- 票 2：写完所有组件
- 票 3：拼所有页面

问题：任何一票都无法独立验证，最后才发现拼不起来。

**正确做法**（纵向切片 / tracer bullet）：每张票是一条**窄但完整**的路径，从数据到界面到验证全部打通。

例如"设备状态总览页"可切为：
- 票 1：骨架 + 一台设备的真实数据卡片（打通数据链路）
- 票 2：扩展到设备列表 + 状态色 + 异常态
- 票 3：趋势图接入 + 图表封装
- 票 4：多分辨率适配 + 视觉基线入库

每张票完成时都是**可演示、可验证**的。

## 每张票必须包含

```markdown
# <编号> — <标题>

**要交付的行为**：从使用者视角描述这个票让什么变得可用（不是逐层实现清单）。

**依赖**：必须完成后才能开始的票编号；无则写"无，可立即开始"。

**验收标准**：
- [ ] 可勾选、可复现的标准 1
- [ ] 可勾选、可复现的标准 2

**影响面**：改动了哪些共享组件/图表/样式，需回归哪些页面。
```

## 拆票粒度

一张票应满足：

- 能在**一个专注的工作单元**内完成，不必跨多天。
- 验收标准全部可客观判定（有截图、有数据、有测试）。
- 不包含"顺便优化一下"这类模糊内容。

## 排序：按依赖走前沿

先画依赖关系，再按"前沿"（依赖已全部完成的票）推进。不要在依赖未满足时提前动工。

## 与设计真源的关系

- 涉及视觉的票，验收标准必须引用具体 token 名称，不能写"颜色好看"。
- 如需偏离真源，在开票时说明并登记到 `pages/`。

## Gate 检查

- [ ] 所有票是纵向切片，可独立验证
- [ ] 每张票有明确依赖与可复现验收标准
- [ ] 视觉类票引用了具体 token
- [ ] 无"顺便优化"类模糊内容
- [ ] 依赖顺序清晰，无循环依赖
